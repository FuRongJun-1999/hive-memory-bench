> 题库：`mcq/reasoning/题目_多跳六元素_rubric92_平衡掩码.json`（92 题 / 552 断言，3 真 3 假）

| 层 | 口径 | 读数 | φ |
|---|---|---|---:|
| **检索层**（时间桶推断） | `scripts/bench_state_track.py`：槽位共现推桶、桶内核对；纯确定性、不调模型 | **top-1 94.20%** | — |
| **判定层**（灵枢自带确定性核对） | 同上，桶内六要素逐字核对 → 判真/假 | **平衡准确率 0.9783**（tp266/tn274/fp2/fn10） | — |

## 1. 复现（逐位一致）

```bash
HMB=<hive-memory-bench 本地检出> python scripts/bench_state_track.py
# → {"n": 552, "scope_infer_top1": 0.942, "oracle_judge_balanced": 0.9783,
#    "tp": 266, "tn": 274, "fp": 2, "fn": 10}
```

与 #844 的定标表一致（含消融：加不加「第N章」都是 94.20%，因为推桶只用了其余五槽）。词面基线 90.76% 的对照也在该脚本注释里。

## 2. 端到端为什么只有 65.2%

`prepare --mode-pack timepack` 给每道题装配**1 万字**（≈4 章，按票王章 + 时间顺序补齐），6 条断言共享这一份材料。判分 `deepseek-chat`、T=0、max16、单断言：

| | 值 |
|---|---:|
| n | 552（应答 552） |
| tp / tn / fp / fn | 89 / 271 / 5 / 187 |
| TPR（真断言判「是」） | 32.2% |
| TNR（假断言判「否」） | 98.2% |
| 平衡准确率 | **0.6522** |
| φ | 0.4048 |
| 材料均值 | 10,006 字 |

**归因（与前面几轮同一套）**：材料从 2.7k 涨到 10k，模型「看见格子多但核对不上」→ 一律答否（187 条真断言被判死，TNR 98.2% 而 TPR 只有 32.2%）。这与 OpenViking（25k→76.6%）、千问 RAG（9.7k→69.6%）的损耗方向一致：**材料规模不是越大越好**。

**关键区别**：灵枢的 0.9783 不是 LLM 判出来的，是它**自己在桶内逐字核对槽位**得出的；一旦换成「LLM 判官 + 给材料」这套七臂口径，它的分数就由材料投喂方式决定，而不是由它的判定能力决定。

## 3. 放到同尺里

| 臂 | 材料 | 平衡准确率 | φ | 判官 |
|---|---:|---:|---:|---|
| 只给所引章节（上限锚） | 2,670 | 87.3% | 0.748 | LLM |
| dsh-memu-memory（两跳，章节） | 5,379 | 87.3% | 0.747 | LLM |
| dsh-memu-memory（两跳，块） | 2,061 | 83.7% | 0.681 | LLM |
| surfcore 0.8.6 | 25,250 | 82.1% | 0.642 | LLM |
| OpenViking 0.4.22 | 25,484 | 76.6% | 0.556 | LLM |
| 千问 RAG | 9,727 | 69.6% | 0.448 | LLM |
| **灵枢（端到端，timepack）** | **10,006** | **65.2%** | **0.405** | LLM |
| dsh-rofm 1.4.4 | 11,882 | 63.0% | 0.331 | LLM |
| 灵枢（**自带确定性核对**，不属于本表口径） | — | **97.83%** | — | **无模型** |

**结论**：灵枢的强项在「检索 + 确定性核对」这一体两翼——推桶 94.20%，核对 97.83%；但它**不给 LLM 喂小材料**，所以在「LLM 判官」这套横比口径里，它被自己的投喂策略（1 万字/题）压到 65.2%。要并列就必须声明判官：**LLM 判官 65.2% vs 自带判定 97.8%，两者的差别是「谁在判」，不是「记没记住」。**

## 4. 若要继续优化（可选）

1. **压材料**：把 `--mode-pack` 从 `timepack`（1 万字）换到 `cited` / `cited_ctx`（所引章节 ≈2.7k），同判官可望回到 ~87%，验证「材料规模」是主因；
2. **两级判**：先用确定性核对判掉八成，剩下的低置信断言再交 LLM —— 这样既保留 97.83% 的判定力，又让 LLM 判官口径可比；
3. `chapters_text()` 只认 `## 第N章`，而语料第 18 章是单 `#` 标题（实测给出 22 章）——修掉可让推桶与材料装配更准。

## 5. 边界

单次运行；判分模型 `deepseek-chat`（换模型 TPR 会漂 3–5 点）；`timepack` 的 1 万字是脚本默认（`PACK_CHARS=10000`），不是灵枢线上默认注入量；`bench_state_track.py` 的核对是「槽位值逐字出现在推断桶内」，不等于线上 `cg.search` + `judge` 的完整链路。
