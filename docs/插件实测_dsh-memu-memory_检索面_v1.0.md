# 插件实测：dsh-memu-memory 1.3.1 的检索面（v1.0）

> 日期：2026-11-10 · 被测：`dsh-memu-memory@1.3.1`（npm，MIT，面向长篇 RP/陪伴对话的 DSH 记忆插件）
> 题库：`mcq/reasoning/题目_多跳六元素_rubric92_平衡掩码.json`（92 题 / 552 条断言，3 真 3 假）
> verdict 产出：`deepseek-chat`、T=0、max_tokens=16、单断言；判分为机械比对 —— 与《新推理库实测》《千问RAG与OpenViking补测》同尺

---

## 0. 一句话

**（并列新增：灵枢 93.1%/94.3%，见 §3）** 它的检索很强（所引章 top-1 98.4%、top-k 99.8%），但它默认只注入「标题卡」（每问约 285 字）——单步判分等于没记忆（50.0%/φ=0）；把「按 id 取正文」这一步补上（它就是靠 `memu_private_recall` 工具再取），同一个插件到 87.3%/φ=0.747，与「只给所引章节」的上限锚持平。**

---

## 1. 两种读法，两个数（务必分开看）

| 读法 | 材料 | 平衡准确率 | φ | TPR | TNR | 整题 6/6 |
|---|---|---:|---:|---:|---:|---:|
| **A. 注入即判**（单步，模型只看插件这一回合注入的东西） | 标题卡 ≈285 字 | **50.0%** | 0.000 | 0.0% | 100.0% | 0/92 |
| **B. 注入 + 展开正文**（模拟 agent 调 `memu_private_recall` 取回这 2 条） | 23 章里取 2 章 ≈5,379 字 | **87.3%** | 0.747 | 89.5% | 85.1% | 42/92 |
| B′. 同上，但语料按 1,200 字切块（60 块） | 取 2 块 ≈2,061 字 | **83.7%** | 0.681 | 76.4% | 90.9% | 29/92 |
| B″. 章节粒度 + **消融**：query 去掉「第N章「标题」」 | ≈5,297 字 | **86.6%** | 0.733 | 84.4% | 88.8% | 35/92 |

**A 不是「检索差」，是设计**：插件注入的是记忆**索引**（`<memory-context>` 里的标题卡，明写「标题卡取正文用 memu_private_recall」），正文要靠工具二次取。所以拿一次性判分的基准去量它，它必然读作「零信号」。

## 2. 召回质量（这才是它真正的强项）

| 粒度 | 所引章 top-1 | top-k | 每问召回条数 | 空召回 |
|---|---:|---:|---:|---:|
| 章节（23 章） | **98.4%** | 99.8% | 2.0 | 0 |
| 块（60 块） | 97.5% | **100%** | 2.0 | 0 |
| 章节 · **去掉章节号消融** | **95.5%** | 98.9% | 2.0 | 0 |

- 断言 query 里自带「第N章「标题」」，等于半个答案——**消融显示它不靠这个**：去掉后 top-1 只掉 **2.9 点**（98.4→95.5），平衡准确率只掉 0.7 点。
- 默认配置下它给的是 `privateTopK=5` + `relevanceThreshold=0.4`，实测每问只有 **2 条**过阈——不是「给一堆」，是「给两条准的」。

## 3. 与九臂并列（同尺，2026-11-10 加入灵枢两臂）

| 臂 | 材料均值 | verdict 产出者 | 平衡准确率 | φ | 备注 |
|---|---:|---|---:|---:|---|
| **灵枢（生产检索 top-3）** | ~5,300 | LLM 作答（deepseek-chat） | **94.3%** | 0.888 | 检索（非 oracle）；⚠️ 批量判（6 条/次） |
| **灵枢（生产检索 top-1）** | 2,670 | LLM 作答（deepseek-chat） | **93.1%** | 0.864 | 检索（非 oracle）；⚠️ 批量判（6 条/次） |
| 只给所引章节（上限锚） | 2,670 | LLM 作答 | **87.3%** | 0.748 | oracle |
| **dsh-memu-memory（章节粒度，展开正文）** | 5,379 | LLM 作答 | **87.3%** | 0.747 | 两跳；与锚持平 |
| **dsh-memu-memory（块粒度，展开正文）** | 2,061 | LLM 作答 | **83.7%** | 0.681 | 两跳；材料只有 surfcore 的 8% |
| surfcore 0.8.6 | 25,250 | LLM 作答 | 82.1% | 0.642 | 一跳，全文摊开 |
| OpenViking 0.4.22 | 25,484 | LLM 作答 | 76.6% | 0.556 | 一跳，整章堆叠 |
| 千问 RAG（qwen3-embedding-4b） | 9,727 | LLM 作答 | 69.6% | 0.448 | 一跳，碎片 |
| dsh-rofm 1.4.4 | 11,882 | LLM 作答 | 63.0% | 0.331 | 一跳 |
| dsh-world 0.7.3 | 2,937 | LLM 作答 | 51.3% | 0.113 | 一跳 |
| dsh-soul 2.0.0 | 179 | LLM 作答 | 50.0% | 0.000 | 一跳 |
| 闭卷 | 0 | — | 50.0% | 0.000 | 下界 |
| **dsh-memu-memory（注入即判）** | 285 | LLM 作答 | **50.0%** | 0.000 | 单步；等于没记忆 |
| 灵枢（系统自身确定性核对） | — | **系统自身** | **97.8%** | — | **不属于本表口径**（verdict 不由 LLM 产出） |

**并列时必须标注的差异**：

1. **memu 是两跳**（注入标题卡 → 按 id 取正文），其余多为一跳；跨系统排名要声明，否则「87.3%」会被误读成「一跳就给了 5,379 字」。
2. **灵枢两臂的材料来自它自己的检索**（`scopeselect` 选时间桶，top-1 命中率 97.83% / top-3 99.82%），不是 oracle；
   而「只给所引章节（上限锚）」是 oracle。⇒ 灵枢在**材料更差**的前提下分数更高。
3. **灵枢两臂是批量判**（每请求 6 条断言），其余是单断言判。批量可借同题「3 真 3 假」结构校准，
   预计比单断言高 5–7 点；**改为单断言后需重测**，届时本表要更新。
4. **判分器对所有行都是机械比对**（`pick == answer`），从来不是变量；
   可比的差异只在「verdict 由谁产出 / 提示词 / 材料来源 / 判分粒度」四列。

### 3.1 灵枢为什么能低于 memu 的字数、高于它的分数

| 指标 | 灵枢 | memu |
|---|---:|---:|
| 所引章 top-1 | **97.83%**（生产口径，含消融前后同值） | 98.4% |
| 所引章 top-k | **99.82%**（k=3） | 99.8% |
| 材料均值（top-1 臂） | 2,670 字 | 2,061–5,379 字 |
| 平衡准确率（同作答题、同判分器） | **93.1%** | 83.7–87.3% |

两者召回几乎持平（97.83% vs 98.4%），分数差主要来自**材料装配**：
灵枢给的是「该时间桶原文 + 章标题行」，memu 给的是「标题卡 + 展开的 2 条正文」。
灵枢这条路径的判定另有**确定性核对**（0.9783），但那个 verdict 不由 LLM 产出，故单列在表末、不进横比。

复现：见 [`灵枢实测_三种口径与统一尺度_v2.0.md`](./灵枢实测_三种口径与统一尺度_v2.0.md) §9。

## 4. 归因：它为什么能只有 2 千字还到 83.7%

与《千问RAG与OpenViking实测》的同一套归因口径对得上：**决定分数的是「材料里六格齐不齐、是不是同一场景」，不是字数。**

- 它的召回几乎是「章节级精确」：top-1 98.4%，等于直接给出「这一章」；
- 展开 2 章后，六元素几乎全在（块粒度 2,061 字也能到 83.7%，比 9,727 字的千问 RAG 高 14 点）；
- 而 OV 的 25,484 字（十整章）只有 76.6% —— 多出来的九章是纯噪声。

## 5. 复现

```bash
# 1) 取包（不装依赖，先解包）
npm pack dsh-memu-memory            # 得 dsh-memu-memory-1.3.1.tgz → 解包
cd package && npm install --omit=dev --no-audit --no-fund --ignore-scripts

# 2) 接宿主包（插件里 import '@deepseek-ai/dsh-llm' 与 '@deepseek-ai/dsh-tools'）
#    本机：junction 到 DSH 0.2.1-rc.5 的 node_modules/@deepseek-ai/{dsh-llm,dsh-tools}
mklink /J node_modules\@deepseek-ai\dsh-llm   <DSH>\node_modules\@deepseek-ai\dsh-llm
mklink /J node_modules\@deepseek-ai\dsh-tools <DSH>\node_modules\@deepseek-ai\dsh-tools

# 3) 跑召回台（隔离根；不碰用户真实库）
node _memu_hive_bench.mjs      # 两种粒度 → memu_{chapters,blocks}_recall.jsonl
node _memu_strip.mjs           # 消融（query 去掉章节号）
python _memu_expand_judge.py   # 命中率 + 展开正文判分
```

**踩坑（都已修）**：① 只解包 tarball 缺 `fflate` 等 17 个运行时依赖 → 要 `npm install --omit=dev`；
② 插件 `lib/inject.js` 直接 import 宿主包 → 探针环境需要 junction 宿主 `@deepseek-ai/dsh-llm`/`dsh-tools`；
③ 语料是 CRLF，JS 的 `.` 不吃 `\r`，章节正则会整段不命中（我第一次就拿到 0 条目、材料全空的假数据）→ 读入先归一化换行。

## 6. 边界

1. **不是端到端 agent 实测**：我把它的生产召回函数当库调用（`privateRecall` + `buildRecall`），没跑真实会话；两跳读法里的「取正文」是我按召回 id 代打的。
2. **只测了默认 lexical 后端**，没启用 embedding/向量模式；开向量后的读数会变，须重测。
3. **题集是 OOD**：它是 RP/陪伴向插件，本题库是六元素事实断言；这不构成对它在主场表现的评价。
4. 单次运行；作答模型换掉，TPR 会漂 3–5 点（判分器不动，恒为机械比对）。
5. `buildRecall` 的预算用默认（`turnTokens=800`）；调大预算会注入更多标题卡，但 top-k 已 99.8–100%，预计只增噪声——未实测。
